1.1. НАЗНАЧЕНИЕ СИСТЕМЫ

Arizona Lavka Marketplace — это профессиональная full-stack платформа для
мониторинга и анализа marketplace игрового сервера Arizona RP (GTA 5 Online).

Основное назначение:
- Предоставление игрокам инструмента для просмотра актуальных предложений
  marketplace (продажа/покупка предметов)
- Генерация торговых конфигов для автоматизированных ботов
- Исторический анализ цен и трендов на 33 серверах
- Отслеживание изменений цен в реальном времени

1.2. ЦЕЛЕВАЯ АУДИТОРИЯ

- Игроки Arizona RP, занимающиеся торговлей на marketplace
- Владельцы торговых ботов для автоматизации
- Аналитики игровых экономик
- Исследователи виртуальных рынков

1.3. ОСНОВНЫЕ ВОЗМОЖНОСТИ

✓ Мониторинг предложений marketplace в реальном времени
✓ Поиск предметов по названию с фильтрацией
✓ Фильтрация по серверам (33 сервера Arizona RP)
✓ Сортировка по цене (возрастание/убывание)
✓ Просмотр лавок игроков с детальной информацией
✓ Генерация торговых конфигов с IQR фильтрацией выбросов
✓ Исторический анализ данных (тренды, ликвидность)
✓ JWT аутентификация с refresh токенами
✓ История сгенерированных конфигов
✓ Избранные предметы (запланировано)
✓ Уведомления об изменении цен (запланировано)

3.1. МОДУЛЬ 1: АУТЕНТИФИКАЦИЯ И АВТОРИЗАЦИЯ

3.1.1. Регистрация пользователя
Входные данные:
- username (3-50 символов)
- email (валидный email)
- password (минимум 8 символов)
- first_name (опционально, до 100 символов)
- last_name (опционально, до 100 символов)

Процесс:
1. Валидация входных данных (Pydantic)
2. Проверка уникальности username и email
3. Хеширование пароля (bcrypt, 12 rounds)
4. Создание записи в БД
5. Автоматический вход (генерация токенов)

Выходные данные:
- Объект пользователя (id, username, email, is_premium, created_at)
- Access token (JWT, 30 минут)
- Refresh token (JWT, 7 дней)

Endpoint: POST /api/auth/register

3.1.2. Вход пользователя
Входные данные:
- username или email
- password

Процесс:
1. Поиск пользователя по username/email
2. Проверка блокировки аккаунта (locked_until)
3. Проверка пароля (bcrypt.compare)
4. Сброс счётчика попыток при успехе
5. Увеличение счётчика при ошибке
6. Блокировка после 5 неудачных попыток (15 минут)
7. Генерация пары токенов

Выходные данные:
- Access token
- Refresh token

Endpoint: POST /api/auth/login

3.1.3. Обновление access токена
Входные данные:
- refresh_token

Процесс:
1. Валидация refresh токена (JWT decode)
2. Проверка типа токена (type=refresh)
3. Поиск пользователя в БД
4. Проверка соответствия refresh_token в БД
5. Генерация новой пары токенов
6. Обновление refresh_token в БД

Выходные данные:
- Новый access token
- Новый refresh token

Endpoint: POST /api/auth/refresh

3.1.4. Выход пользователя
Входные данные:
- Access token (в заголовке Authorization)

Процесс:
1. Получение текущего пользователя из токена
2. Очистка refresh_token в БД (отзыв)
3. Логирование выхода

Выходные данные:
- Сообщение об успешном выходе

Endpoint: POST /api/auth/logout

3.1.5. Получение информации о пользователе
Входные данные:
- Access token (в заголовке)

Процесс:
1. Валидация токена
2. Получение пользователя из БД

Выходные данные:
- Профиль пользователя (id, username, email, first_name, last_name, is_premium, created_at)

Endpoint: GET /api/auth/me

3.1.6. Защита от brute-force
- Максимум попыток входа: 5
- Время блокировки: 15 минут
- Счётчик хранится в БД (login_attempts, locked_until)

3.1.7. Требования к паролям
- Минимальная длина: 8 символов
- Хеширование: bcrypt с солью
- Хранение: только хеш в БД

3.2.1. Получение предложений (offers)
Входные данные (query parameters):
- search_term (строка, опционально)
- server_id (int, -1..32, опционально)
- sort_order (asc/desc/none, по умолчанию none)

Процесс:
1. Получение данных из внешнего API (arz.market)
2. Кэширование ответа (TTL 30 секунд)
3. Парсинг параллельных массивов:
   - items_sell, price_sell, count_sell
   - items_buy, price_buy, count_buy
4. Нормализация данных (преобразование в Offer объекты)
5. Фильтрация по search_term (case-insensitive)
6. Фильтрация по server_id
7. Сортировка по price (asc/desc)
8. Подсчёт уникальных серверов

Выходные данные:
{
  offers: [
    {
      type: "sell"|"buy",
      itemId: int,
      itemName: string,
      price: number,
      count: number,
      username: string,
      lavkaUid: string,
      serverId: int,
      serverName: string,

  total: int,
  servers: int

Endpoint: GET /api/marketplace/offers

3.2.2. Получение списка серверов
Процесс:
1. Чтение из констант (SERVER_NAMES)
2. Формирование списка

Выходные данные:
{
  servers: [
    { id: int, name: string }
  ],
  total: int (33)
}

Endpoint: GET /api/marketplace/servers

3.2.3. Получение списка лавок на сервере
Входные данные:
- server_id (int, 0..32)

Процесс:
1. Получение данных из API
2. Фильтрация по server_id
3. Группировка по lavkaUid
4. Подсчёт items_sell и items_buy
5. Сортировка по totalItems (убывание)

Выходные данные:
{
  lavkas: [
    {
      lavkaUid: string,
      username: string,
      serverId: int,
      serverName: string,
      sellCount: int,
      buyCount: int,
      totalItems: int
    }

Входные данные:

Процесс:

   - items_sell, price_sell, count_sell

Выходные данные:

    {
      itemId: int,

Процесс:

Выходные данные:

- TTL: 30 секунд
- Max size: 100 записей

- Key: "marketplace_data"

3.3. МОДУЛЬ 3: ГЕНЕРАЦИЯ ТОРГОВЫХ КОНФИГОВ

3.3.1. Генерация конфига
Входные данные:
- server_id (int, 0..32)
- mode (SELL|BUY)
- percentage (float, -50..50)
- save_to_history (bool, по умолчанию true)

Процесс генерации:

Этап 1: Сбор данных
1. Получение данных из marketplace API
2. Фильтрация по server_id
3. Извлечение предметов для режима:
   - SELL: items_sell, price_sell
   - BUY: items_buy, price_buy
4. Группировка по item_id:
   {
     item_id: (item_name, [price1, price2, ...])
   }

Этап 2: Анализ каждого предмета
Для каждого item_id:

2.1. Расчёт текущей цены (IQR метод):
    a. Сортировка цен
    b. Расчёт Q1 (25-й перцентиль) и Q3 (75-й перцентиль)
       - Линейная интерполяция для точности
    c. IQR = Q3 - Q1
    d. Границы: [Q1 - 1.5*IQR, Q3 + 1.5*IQR]
    e. Фильтрация выбросов (за пределами границ)
    f. Если отфильтровано >50% → использовать медиану всех
    g. Медиана отфильтрованных цен

2.2. Загрузка исторических данных:
    - Чтение из data/info_users_{mode}_{server}.json
    - Кодировка: cp1251
    - Поиск по item_name (с конвертацией UTF-8 ↔ cp1251)

2.3. Расчёт исторических метрик:
    - Средняя цена за 7 дней
    - Средняя цена за 30 дней
    - Тренд (up/down/stable, порог 5%)
    - Ликвидность (0-100, по дням с торгами и объёму)

2.4. Расчёт взвешенной цены:
    - weight_current = 0.40 (40%)
    - weight_historical = 0.35 (35%)
    - weight_trend = 0.25 (25%)
    - weighted_price = (current_median * 0.40) + 
                       (historical_avg * 0.35) +
                       (trend_adjustment * 0.25)

2.5. Расчёт уверенности (0-1):
    - Фактор 1: Количество текущих предложений (0-0.3)
      * ≥10: 0.3, ≥5: 0.2, ≥2: 0.1
    - Фактор 2: Дней исторических данных (0-0.3)
      * ≥14: 0.3, ≥7: 0.2, ≥3: 0.1
    - Фактор 3: Ликвидность (0-0.25)
      * liquidity_score / 100 * 0.25
    - Фактор 4: Стабильность цены (0-0.15)
      * (1 - variance) * 0.15
    - Уровни:
      * VERY_HIGH: ≥0.90
      * HIGH: ≥0.75
      * MEDIUM: ≥0.50
      * LOW: ≥0.25
      * VERY_LOW: <0.25

2.6. Применение процентной корректировки:
    - adjusted_price = weighted_price * (1 + percentage/100)

2.7. Округление:
    - HIGH/VERY_HIGH: точное округление
    - MEDIUM: до 5
    - LOW/VERY_LOW: до 10
    - Минимум: 1

Этап 3: Формирование конфига

Кодировка: cp1251 (Windows-1251)

3.4.2. Расчёт тренда цены
Входные данные:
- item_name
- mode (buy|sell)
- days (7|30)

Процесс:
1. Получение истории торгов
2. Сортировка по дате (убывание)
3. Выборка последних N дней
4. Расчёт метрик:
   - current_price: цена сегодня
   - old_price: цена N дней назад
   - avg_price: среднее арифметическое
   - min_price, max_price
   - price_change: current - old
   - price_change_percent: (change / old) * 100
5. Определение тренда:
   - up: change_percent > 5%
   - down: change_percent < -5%
   - stable: иначе

Выходные данные:
{
  trend: "up"|"down"|"stable",
  current_price: number,
  avg_price: number,
  min_price: number,
  max_price: number,
  price_change: number,
  price_change_percent: number,
  volume: number,
  data_points: number
}

3.4.3. Расчёт ликвидности
Входные данные:
- item_name
- mode
- days (30)

Процесс:
1. Получение истории торгов
2. Сортировка по дате
3. Расчёт метрик:
   - days_with_trades: количество дней с активностью
   - total_volume: сумма количеств
   - avg_daily_volume: total_volume / days_with_trades
4. Нормализация:
   - days_score: (days_with_trades / days) * 100
   - volume_score: (total_volume / 1000) * 100
5. Итоговый score:
   - liquidity_score = days_score * 0.4 + volume_score * 0.6

Выходные данные:
- liquidity_score (0-100)

3.4.4. Расчёт справедливой цены
Входные данные:
- item_name
- mode
- percentage

Процесс:
1. Получение тренда за 7 дней
2. Получение тренда за 30 дней
3. Взвешенное среднее:
   - avg_7d * 0.5 + avg_30d * 0.3 + current * 0.2
4. Применение percentage
5. Округление

Выходные данные:
{
  fair_price: number,
  confidence: "high"|"medium"|"low",
  metrics: {...}
}
